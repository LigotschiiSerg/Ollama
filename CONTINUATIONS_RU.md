# Объединение таблиц с нескольких страниц

Исправление не требует нового OCR. Оно работает с уже извлечёнными таблицами:
- повторные шапки допускают небольшие OCR-ошибки и смещения строк;
- продолжения без шапки сравниваются по типам значений в колонках;
- длинные текстовые матрицы тоже могут продолжаться на следующей странице;
- разница на **одну пропущенную пустую колонку** допускается, и при экспорте эта колонка заполняется пустым значением;
- канонические `documents_cell` не меняются, все строки логической таблицы получают `_source_page`.

## Применение к существующей базе

1. Остановить Django и рабочий процесс OCR.
2. Создать резервную копию `db.sqlite3` и `media`.
3. Перенести базу в папку с `manage.py` из данного архива.
4. В активированном `.venv` выполнить:

```powershell
python manage.py migrate
python manage.py check
python manage.py test documents.tests.test_continuation
python manage.py export_pdf_tables
```

После команды посмотреть `python manage.py list_pdf_tables --document 1` — фрагменты с одним ID группы являются одной логической таблицей. В DB Browser открывать физические таблицы `pdf_...`; для объединённой таблицы они содержат `_source_page`.

## Ограничения

OCR продолжает извлекать фрагменты по страницам; они объединяются **после распознавания**. Признаки продолжения не всегда однозначны, особенно если новая таблица начинается сразу на следующей странице с точно такой же структурой. Проверьте результат с PDF. Если алгоритм не уверен, вручную используйте `merge_pdf_tables PREVIOUS_ID NEXT_ID`. При необходимости разъединяйте связь `continues_from` через Django shell и повторяйте `export_pdf_tables`.

Для представленного PDF ожидаются объединения фрагментов со страниц 3–7, 8–9, 11–13, 15–16. Они были выявлены по содержимому `db(5).sqlite3` в отдельной проверке правил, **без запуска Docling/Ollama**. Качество исходного OCR автоматически не исправляется.
